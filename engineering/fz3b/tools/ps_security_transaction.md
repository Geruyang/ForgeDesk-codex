# Fixed PS Security Transaction

This tool is scoped to the five approved v2 Python files and `config.json` in
`/root/fz3b-vision-console-20261009-001`. It is not a general deployment runner.
It never invokes service start/stop, imports the application, or accesses hardware.
It does not establish SSH identity, authentication, operator approval, or board readiness.

## Approval And Request

The remote code hard-pins the five source SHA256 values from the approved manifest
`d0740647bdb4a505414e626839c5eff811091b25612e09cce5487a459a631c09`.
Compilation alone cannot authorize different Python source. Host generation also
requires the exact approved manifest bytes. `config.example.json` is not deployed.

Deploy request JSON has exactly these fields:

```json
{
  "schema": 1,
  "mode": "deploy",
  "run_id": "ps-security-20261016-001",
  "expected_sha256": {
    "vision_app/board_agent.py": "<exact-current-64-lowercase-hex>",
    "vision_app/camera.py": "<exact-current-64-lowercase-hex>",
    "vision_app/image_boundary.py": null,
    "vision_app/protocol.py": "<exact-current-64-lowercase-hex>",
    "vision_app/upload_source.py": "<exact-current-64-lowercase-hex>",
    "config.json": "<exact-current-64-lowercase-hex>"
  },
  "payloads": {
    "vision_app/board_agent.py": "<approved-source-base64>",
    "vision_app/camera.py": "<approved-source-base64>",
    "vision_app/image_boundary.py": "<approved-source-base64>",
    "vision_app/protocol.py": "<approved-source-base64>",
    "vision_app/upload_source.py": "<approved-source-base64>"
  }
}
```

The actual board-agent TCP host key is `bind`, shared by control and video ports.
Only `bind` is set to `127.0.0.1`; all other parsed JSON values are retained.
Whitespace/key ordering changes, so preservation is semantic, not byte-identical.
Duplicate keys, non-finite numbers, excessive depth/size, and non-object config fail.

Host-only generation, with every path inside this project:

```text
python -B engineering/fz3b/tools/ps_security_transaction.py --emit REQUEST.json --output STDIN_PAYLOAD.py --approved-manifest output/hardware/2026-10-16-continuation/deployment-bundle-v2/manifest.json
```

Output creation is exclusive and cannot replace an existing payload file. Generation
does not run the remote transaction. Root alone may transmit the generated bytes to
the already-verified board's `python3 -B -` stdin under the separate hardware grant.

## Filesystem Transaction

The remote process requires Linux root and opens every fixed application directory
component with `O_NOFOLLOW|O_DIRECTORY`. Directory identities remain anchored by fd;
directories must be root-owned and not group/world-writable. Existing targets must
be bounded regular, single-link, root-owned files without special or writable-group/
other modes. Reads recheck inode/extent/metadata, and symlinks/special files fail closed.

All source payloads are hash-checked and compiled without import in the actual remote
interpreter before target mutation. All six preimages are checked, then a fixed
application-wide durable lease is acquired and the entire old set is checked again.
The latter prevents a stale preparation from undoing a different completed run.

The fixed lease `.forgedesk-ps-transaction.lock` uses exclusive creation, nofollow,
mode 600, fd fsync, and parent fsync. Its contents bind `run_id` and the exact
transaction manifest SHA. A nonblocking exclusive `flock` also prevents concurrent
same-run rollback while the original process remains alive. No PID is used to steal
or clear leases. Disconnect/process death releases flock, not the durable lease.

Backups and staged files are exclusively created in
`.forgedesk-ps-backups/<run_id>/` with parent/run mode 700. Original bytes and their
hashes remain preserved. Every stage/backup/manifest is fsynced and verified before
the first replacement. A repeated run ID cannot overwrite an existing backup.
Replacements are individually atomic `os.replace` operations followed by directory
fsync, not a multi-file atomic commit.

Service state is read only with a fixed `systemctl show` command. The known unit must
be loaded, inactive, and `MainPID=0` before filesystem creation and repeatedly during
commit/recovery. This is only a systemd gate: it does not prove that manually started
agents, socket owners, PL/R5 jobs, loaders, or other hardware consumers are quiescent.
The root-owned external workflow must verify those conditions and hold its own
exclusive hardware lock throughout. No request boolean can replace those checks.

## Results And Recovery

- `deployed`: all six new hashes verified; lease removal and parent fsync succeeded.
- `failed`: no unverified target outcome; when this run owned a lease, the entire old
  set was proven restored before the lease was released. Inspect the error and report.
- `unknown`: uncertain mutation, incomplete recovery, loss of service quiescence,
  metadata/lock cleanup error, or another unexpected state. Keep the outer hardware
  lock, do not start the service, and do not retry deployment under a fresh run ID.
- `rolled_back`: every original hash/absence verified and the lease safely released.

Automatic recovery only considers files for which this run had actually attempted
`replace`, registered before the call to account for rename-success/fsync-failure.
Matching a new hash alone does not establish ownership and cannot authorize undoing
another run's data. A foreign mutation remains untouched and produces `unknown`.

Unknown outcomes retain the durable lease. If lease unlink succeeds but directory
fsync fails, the tool attempts to recreate the same seal. If storage failure also
prevents recreation, the report truthfully has `persistent_lock_retained=false` and
`persistent_lock_uncertain=true`; it cannot guarantee a durable lock on broken storage.
Similarly, a cleanup exception after confirmed release cannot recreate the already
completed transaction by assertion. The outer exclusive lock remains mandatory.

Independent rollback request:

```json
{"schema":1,"mode":"rollback","run_id":"ps-security-20261016-001","manifest_sha256":"<transaction-manifest-sha-from-deploy-report>"}
```

The same generation command and approved v2 manifest are required. Rollback only
reads the fixed run's `manifest.json`, verifies its caller-provided seal and fixed
schema/approved source hashes, checks every backup hash, and accepts only exact old
or exact new live bytes. It also independently verifies that the config change was
bind-only. Existing leases must match this exact run and manifest, with no live flock
holder. An absent lease can be exclusively reacquired for an ordinary post-deploy
rollback. Already-restored entries permit retrying a partially completed rollback.

Old backups/manifests are never overwritten. The added image module is moved to a
unique `*.displaced.<uuid>` evidence file when restoring its original absence;
directories and original backup files are not deleted. Recovery stage filenames are
also unique, allowing a retry without overwriting prior recovery evidence.

If the process failed before a valid manifest was durably created, or foreign files
are observed, automatic rollback may be intentionally unavailable. Preserve the
lease and evidence for explicit operator reconciliation; do not guess or clear it.

## Verification Scope

`test_ps_security_transaction.py` uses only an in-memory filesystem and mocked Linux
syscalls/service reader. It covers stale-run interleaving, unknown lease retention,
lost-connection reentry, wrong manifest/backup/live hashes, special/link/size/mode
gates, payload pins, config preservation, staged writes, and failures before/after
rename. Python 3.6 grammar is checked locally. These are not claims that the actual
Linux filesystem transaction, service lifecycle, SSH transport, complete application,
or installed board behavior has passed. No real service or SSH is exercised by tests.
