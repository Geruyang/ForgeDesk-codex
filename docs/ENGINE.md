# Codex Engine Adapter

The adapter uses the official Codex app-server over bidirectional stdio JSONL. Protocol types under `schemas/` were generated from `codex-cli 0.162.0-alpha.17.2` with no `--experimental` flag. `schemas/provenance.json` records the generator binary hash and generated tree hash. Runtime initialization rejects a different engine version.

## Integration

Import `CodexAdapter`, `EngineEvent`, `EngineApproval` and `EngineState` from `packages/engine-adapter/index.ts`. Required constructor options are absolute `executable`, absolute product-owned `home`, and `onEvent`. Optional `processHost` selects the native Job Object wrapper. `env` accepts only `FORGEDESK_RUNNER_*` and `ELECTRON_RUN_AS_NODE` overrides. `requestTimeoutMs` defaults to 30000, bounded to 10-120000 for tests and deployment tuning.

The public operations are `start`, `stop`, `models`, `account`, `login`, `startThread`, `resumeThread`, `send`, `steer`, `interrupt`, `approve`, `pendingApprovals`, and the `state` getter. There is no public arbitrary RPC entry point. The adapter does not expose `command/exec`, `thread/shellCommand`, process RPCs or external-agent import RPCs.

`startThread(cwd, model?, developerInstructions?)` and `resumeThread(threadId, cwd, developerInstructions?)` accept app-owned engineering context through the pinned protocol's `developerInstructions` field. Main owns this context; renderer input belongs in ordinary user messages.

`start` completes the `initialize`/`initialized` handshake, reads effective policy and managed requirements, and probes Windows sandbox readiness. States are `stopped`, `starting`, `ready`, `stopping`, and `failed`. Readiness means the connection is usable; it does not establish authentication or the outcome of a coding turn. The official engine is spawned with `windowsHide: true`, `shell: false`, and explicit product `CODEX_HOME`. Existing Codex home paths are rejected. Inherited provider/authentication environment values are removed. The engine's file credential store is explicitly selected for the product directory.

## Permissions and Events

CLI overrides and thread/turn parameters select `on-request`, reviewer `user`, and `workspace-write`. Network access and temporary-directory write exceptions are disabled. Threads require an existing absolute directory, reject overlap with engine data, check effective project policy, and confirm returned cwd and sandbox policy. Every `turn/start` repeats the controlled cwd and sandbox policy. `turn/steer` uses `expectedTurnId` and never silently retries as a new turn. `turn/interrupt` acknowledgment is separate from `turn/completed`; callers must inspect the terminal status.

Each event has `{generation, sequence, method, params}`. Generation numbers use a time/random seed to avoid reusing a previous adapter instance's generation. Sequence increases within a connection. Public events preserve thread, turn and item identifiers; `engine/*` events report connection state, initialization, diagnostics, approvals, request timeout, policy and exit. Authentication result fields are allowlisted. Secret-shaped keys, bearer tokens, API keys and JWTs are redacted before the callback. This is best-effort redaction of engine output, not a promise that arbitrary user files cannot contain unrelated secrets.

Command and file approvals expose scalar `accept`, `acceptForSession`, `decline`, and `cancel` decisions supported by this pinned protocol. An explicit request decision list is intersected with these values. Policy amendment objects are unsupported. Approval delivery matches generation, the request ID including its string/number type, and an allowed decision; one request can only be resolved once. `pendingApprovals()` returns copies for a window reload. A server-resolution event removes a stale pending request; restart and exit clear pending approvals. Engine permission grants are independent of device authorization.

MCP tool confirmations enter the same approval queue only for the configured `engineering` server, a thread loaded in this connection, a nonempty correlated turn ID, `mode: "form"`, and `_meta.codex_approval_kind: "mcp_tool_call"`. The schema must be an object with empty `properties`, absent/empty `required`, and no keys beyond `type`, `properties`, and `required`. Requests explicitly requiring user input are unsupported. Each request is bounded to 32 KiB. This scope matches the real pinned-runtime request observed during `engineering.test`; it is not a general form renderer.

These confirmations expose only `accept`, `decline`, and `cancel`. The reply uses `{action, content, _meta}`: accept sends `content: {}`, decline/cancel send `content: null`, and `_meta` is always null. Requested `persist: ["session", "always"]` metadata is never copied into the reply, so acceptance applies only to the current callback. No session/always option is offered. URL, OpenAI-form modes, nonempty schemas, missing approval markers, other servers, standalone uncorrelated turns and unknown constraints are cancelled. Pending IDs, generation checks, reload copies, resolution notifications, duplicate-ID failures and queue limits apply to MCP confirmations as well. Device authorization remains a separate runner requirement.

Permission-profile approval grants no extra permissions. Unsupported user-input and other server requests receive JSON-RPC method-not-found errors. Unknown notifications are sampled through bounded diagnostics. Protocol lines and outgoing buffered data have a 4 MiB ceiling, client requests are limited to 64, approvals to 128, and diagnostic samples to 100 per connection. Protocol violations or consumer callback failure fail the connection. Exit rejects pending client requests. Request timeout records an unknown outcome and never replays a side effect.

Elicitation diagnostics record only bounded shape information: request/thread/turn IDs, engineering/other server classification, mode, a redacted message sample, and schema/metadata outlines. Outlines have depth, collection and byte budgets; string leaf values become type labels except fixed protocol enumerations. This enables compatibility investigation without persisting tool parameter values or credential metadata.

`stop` closes input, then force-cleans the process tree after a grace period if needed. Production must pass the native `processHost`; it creates the engine suspended, assigns it to a kill-on-close Job Object, and resumes it. The direct-executable development path uses Windows `taskkill /T /F` after the grace period and does not provide the same parent-crash guarantee.

## Windows Sandbox

The current no-administrator implementation explicitly selects `windows.sandbox="unelevated"`. Managed policy that disallows this implementation is rejected. This restricted-token fallback has weaker network isolation than elevated mode and does not support denied read paths, as described by [the official Windows sandbox guide](https://learn.chatgpt.com/docs/windows/windows-sandbox). A later bounded probe confirmed that explicit MXC command startup works on this machine; the release route remains unelevated under the current freeze. MXC integration with authenticated turns/MCP, elevated provisioning, and a device-access bypass matrix remain separate acceptance work. The adapter never enables full access to bypass a setup failure.

## Verification on 2026-10-14

Targeted command: `node --import tsx --test packages/engine-adapter/index.test.ts`. The baseline 14 tests and five added MCP tests passed, 19 total. Tests use a deliberately fake stdio peer to exercise isolation, handshake order, policy rejection, version mismatch, approval ID/generation/decision matching, restart, server resolution, unsupported requests, timeout, exit, malformed and oversized JSONL, unknown notification flooding, controlled turns, app-owned start/resume context, steer preconditions, terminal interrupted status, login URL validation and secret redaction. MCP cases check accept/decline/cancel wire payloads, refusal to grant persistent permission, 16 unsupported form/origin variants, callback resolution, duplicate IDs, queue overflow and bounded redacted diagnostics. These are protocol tests, not live model or device acceptance.

Targeted TypeScript compilation passed with the repository TypeScript dependency. No new module dependencies were added.

The fixture harness creates a separate suite directory for every invocation and unique case directories within it. Ordinary fake-engine requests use a 10000 ms deadline because concurrent full suites and Windows packaging compression made a previous 1000 ms startup allowance fail before the peer could initialize. Approval and terminal-event checks wait on bounded event predicates rather than fixed sleeps. The explicit timeout scenario first waits up to 10000 ms for its fake peer's IPC-ready signal, then attaches the adapter with the original 700 ms request deadline and timeout/no-replay assertions. This separates OS process startup from the deliberately unanswered model request. Product runtime request deadlines were not changed.

Real unauthenticated probes used newly created product directories under `packages/engine-adapter/.protocol-home/`, without reading or copying existing client authentication/configuration. `initialize` and `initialized`, effective policy checks, `model/list`, and `account/read` succeeded. The same probe passed through `vendor/process-host/process-host.exe`. The engine reported Windows `10.0.26200`, x86_64; initial default sandbox readiness was `notConfigured`, and explicit unelevated selection returned `ready`. `account/read` returned `{account:null,requiresOpenaiAuth:true}`.

The live model catalog returned `gpt-6.1-sol` (default, low), `gpt-6-astra` (low), `gpt-6-sol` (medium), `gpt-6-luna` (medium), `gpt-5.6-sol` (low), `gpt-5.6-terra` (medium), `gpt-5.6-luna` (medium), and `gpt-5.5` (medium). Catalog availability is not proof of authenticated inference entitlement.

An additional real no-admin CLI probe ran `codex -c windows.sandbox="unelevated" sandbox --include-managed-config --permission-profile :workspace -- cmd.exe /d /c echo UNELEVATED_OK` with an isolated product home. It returned `UNELEVATED_OK`, exit code 0. This verifies sandbox command startup; outside-workspace write denial, network denial, direct device access denial, authenticated coding, live approval, live steer/interrupt, and installation-path integration were not established by that probe. Login was not initiated by the engine smoke script. Official product login must be completed by the user in the app's public OAuth URL flow.

## Final Bounded Sandbox Probe

Subsequent final installed QA passed the narrow one-shot MCP accept/decline UI path, authenticated repair, steer and interrupt cleanup. See `QA.md` and `ACCEPTANCE.md` for resource-bound evidence; this does not broaden the sandbox probe claims below.

The release-stage probe used the vendored official `vendor/codex/codex.exe`, native `vendor/process-host/process-host.exe`, and a newly created product home at `.runtime/sandbox-probe/run-g849HW/engine`. Its cwd was the sibling `workspace` directory. Every child had a 30000 ms deadline and Job Object cleanup. No elevation, external network or real device action was requested. Raw arguments, stdout, stderr, exit codes, durations and file contents are recorded in `.runtime/sandbox-probe/run-g849HW/result.json`.

The documented explicit MXC command was executed first:

```text
codex -c windows.sandbox=mxc sandbox --include-managed-config --permission-profile :workspace -- cmd.exe /d /c echo MXC_OK
```

It completed in 12567 ms with exit code 0, stdout exactly `MXC_OK\r\n`, empty stderr and no timeout. This establishes native MXC command startup on this host with the selected profile and managed requirements. The current route was not changed during release freeze; switching the adapter to MXC would need planned configuration changes and authenticated turn/MCP regression.

The next two probes selected unelevated mode, workspace-write, no additional writable roots, network disabled, and both temporary-directory write exceptions disabled. They used Node `fs.writeFileSync` under the official `:workspace` sandbox profile. Writing `workspace/allowed.txt` succeeded with exit code 0 and `WRITE_ALLOWED`; the outside process confirmed the expected `WORKSPACE_WRITE_CONTENT\n` bytes. Attempting to overwrite `protected-sibling/protected.txt` failed with exit code 13 and stderr beginning `WRITE_DENIED EPERM EPERM: operation not permitted, open`. The outside process confirmed that `ORIGINAL_PROTECTED_CONTENT\n` remained unchanged. The sibling file used ordinary inherited ACLs; it was not made read-only or independently denied before the sandbox probe.

These results verify one positive workspace write and one denied sibling overwrite in this dedicated test tree. They do not establish every filesystem boundary, network denial, process isolation, device denial or behavior of arbitrary scripts. Repeat with `node --import tsx packages/engine-adapter/sandbox-probe.ts <absolute-codex.exe> <absolute-process-host.exe>`; each run creates a fresh tree and retains its own evidence.

## Snapshot Isolation Receipts

`snapshot-isolation.ts` supplies the T3 model-workspace isolation check. Main first calls the adapter's read-only `snapshotPolicy(projectRoot)` on its current connection with no active turn. This requests real `config/read` for the canonical project and `configRequirements/read`, validates the product's forced permissions, and returns only selected effective/managed permission SHA-256 summaries, canonical project/home, observation time and connection generation. It does not query account credentials or read authentication files. `connectionGeneration` is the read-only getter for the probe's live connection check.

`probeSnapshotIsolation(options)` requires actual project/protected/data/home roots, pinned Codex/process-host executable paths, registered Node executable, this policy evidence and a callback returning the live generation. The protected root must resolve exactly to `dataDir/engineering/snapshots`; product data and model workspace must not overlap. CLI and process-host bytes are checked against the trusted vendor hashes, and Node bytes are included in the binding. Options and policy evidence come only from trusted main, never renderer-submitted receipts or a model-supplied boolean.

The probe executes one fixed Node program through the real Codex sandbox and Job Object host. Exported `SNAPSHOT_SANDBOX_ARGS` repeat the adapter's unelevated/workspace-write, user/on-request reviewer, no-extra-roots, network-disabled and no-temporary-root policy, with `--include-managed-config --permission-profile :workspace`. The program receives only unique probe filenames and a random nonce. It writes a new model-workspace file, attempts to overwrite an ordinary host-created sentinel in the snapshot root, and emits a fixed JSON result. Host verifies the successful workspace bytes, an actual `EPERM`/`EACCES` protected overwrite failure, unchanged sentinel bytes, process exit, binary/policy binding and current generation. It then removes exactly its two uniquely named files. It never changes real source files or requests escalation. Failed denial, unexpected output, timeout, changed connection or incomplete cleanup disables the receipt.

The returned `SnapshotIsolationReceipt` contains `schemaVersion`, method `engine-sandbox-write-denial`, stable `policyDigest`, canonical `projectRoot`/`protectedRoot`, `verifiedAt`, `probeLogRef` and raw-file `probeLogSha256`. Trusted main writes the corresponding JSON log below `dataDir/engineering/isolation-probes`, outside the model workspace. It includes nonce, attempted path, confirmed write denial/workspace write, sentinel before/after hashes, cleanup, fixed code/command and executable hashes, selected policy summaries, child PID/exit and a validated structured result. Arbitrary engine stdout/stderr and environment values are not persisted; their byte counts and hashes are retained. A failed probe never returns a receipt and its top-level `writeDenied` is false even if one physical denial was observed before invalidation.

`calculateSnapshotPolicyDigest(options)` computes the stable binding from canonical roots/home, actual binary hashes, fixed program/arguments and permission summaries. It excludes generation and observation time so a normal reconnect with identical configuration does not rewrite historical B evidence. Generation/time instead enforce a fresh, current probe: main clears its execution cache on engine exit/reconnect, reads live policy again and probes before each new B build. Runner's live digest callback must use that trusted current cache, not a constant closure or persisted success boolean. Configured-permission hashes are conservative bindings, not a proof of every possible execution permission or an unchanged managed policy forever.

Native regression used fresh product directories under `packages/engine-adapter/.test-output`. All three module tests passed with the fixed Windows CLI; the native case verified positive workspace write, protected-root `EPERM`, equal sentinel hashes, no source change and cleanup, then deliberately invalidated the connection during a second real probe and confirmed fail-closed output. The initial raw receipt is `packages/engine-adapter/.test-output/snapshot-gwRPCl/data/engineering/isolation-probes/5434bef3-753c-4368-a4f9-64811e55bced.json`. TypeScript compilation passed. These probes do not establish malicious same-user process resistance, all filesystem APIs, confidentiality, network or device isolation. B remains restricted to fixed trusted read-only snapshot templates; Node permission flags are a second layer. The runner separately owns native OS-sandbox execution from an output-only cwd with input outside it and its own filesystem/SQLite rejection probes. No B template should be enabled merely because Node permission flags are present.
